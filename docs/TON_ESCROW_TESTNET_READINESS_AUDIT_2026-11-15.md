**Status: BLOCKED — do not enable transaction preparation or claim testnet acceptance.**  
**Review type:** internal source, contract, adapter, and test-coverage review. This is not an independent third-party security audit.  
**Contract artifact baseline:** main at 6dafdcf4c462718df14ea024f29fd277c90f6d39 (2026-11-15).

## Executive assessment

The contract and standalone serializer layer are materially more mature than the earlier Issue #214 snapshot. The current source has deadline checks for oracle and resolver messages, terminal-state bounce protection, 2-of-3 Ed25519 quorum checks, typed attempt binding, fixed per-deal roles/assets/amounts, and focused pre-/post-delivery dispute tests. The current contract test file contains **25 named Acton emulator tests**.

The frozen ABI, code BOC, StateInit and message vectors are pinned and reproducible. A successful Acton build on commit 28bb66a6cf8add2c4dce93ca4bfb874179e6404d matches the exact contract source, types and tests currently on main (identical Git blob SHAs); TON Contract CI run #43712458506 passed and reported **25 tests passed**.

Backend API/Preview-route/blocked-action work is coordinated through Draft PR #223, not implemented independently in this PR. At reviewed head 89cb84a, #223 deliberately keeps snapshot construction diagnostic-only and transaction preparation fail-closed because the ORM does not persist the complete immutable snapshot; its newest head still needs a fresh exact-head CI result before integration. The backend workstream also remains subject to review of same-key durable replay and changed-payload conflict semantics. This contract-readiness audit therefore focuses on ABI/BOC/StateInit/message vectors and residual contract lifecycle gaps. Transaction preparation remains disabled. The complete deployment snapshot is not stored in the database, the testnet provider is unconfigured, no getter reconciliation implementation exists, and the API/frontend/backend action contracts contain unresolved workflow mismatches. These are release blockers, not cosmetic follow-ups.

## Contract surface and security controls

The ABI exposes five getters: get_state, get_progress, get_deal_terms, get_oracle_keys, get_resolver_keys. Incoming message declarations cover ActivateDeal, FundDeal, AcceptDeal, OpenDispute, OracleAttestation, ResolveDispute, TimeoutDeal, RecoverUnexpectedNft and the TEP-62 owner notification. Outgoing message declarations are NftTransfer and SettlementMessage.

Positive controls observed:
- Testnet gate checks both the stored network ID and ConfigParam 19 global ID -3; mainnet ID -239 is rejected in an emulator test.
- Per-deal terms pin seller/buyer, exact item and collection addresses, deal salt, principal/reserve/refund/transfer values and six authority keys.
- Oracle and resolver sets each require three distinct nonzero keys and are disjoint; the contract enforces a two-of-three signature threshold.
- Oracle/resolver contexts bind domain, protocol, network, escrow address, salt, action/phase, monotonic attempt and evidence; outgoing routes bind source, destination, item, amount and query ID.
- NFT notifications must originate from the exact configured item and match the expected previous owner, query ID, deadline and exact inline magic+salt payload. Unexpected callbacks persist recovery context and force manual review.
- Buyer funding must equal exact principal plus execution reserve; buyer acceptance is a separate pre-delivery step.
- Oracle and resolver handlers reject messages after the stored deadline; timeout uses strict now > deadline.
- Terminal states SETTLED, REFUNDED, EXPIRED are preserved when a later bounce is received. There is no owner withdraw/upgrade entrypoint in the reviewed source.

Trust boundary: the contract stores a collection address but validates custody using the fixed item address and does not independently prove that the item belongs to the declared collection. Collection authenticity must therefore be established by the trusted verifier/provider and bound into the immutable deal snapshot; an NFT indexer transfer event alone is insufficient.

Current test source has 25 named tests. The principal positive paths include deployment/activation, seller NFT deposit, exact buyer funding, acceptance, stale oracle attempts, signature quorum helper, two dispute outcomes before delivery and two after delivery, deadline checks, and terminal bounce preservation.

## Integration findings — blockers

### B-01 — High: immutable deployment snapshot persistence remains unimplemented (owned by #223/#213)

The pinned adapter requires network/protocol identifiers, authority keys, reserve/refund/transfer economics, action query IDs, deployment/action values and getter facts. The current EscrowDeal ORM row does not persist the complete immutable set. PR #223 makes the snapshot builder diagnostic-only and returns HTTP 503 deployment_snapshot_incomplete rather than generating a partial wallet payload. This is the correct fail-closed behavior, not completion of the schema. Adding the full immutable schema, Alembic migration, DB-level immutability, and PostgreSQL retry/concurrency tests remains open under the coordinated backend track (#223/#213). PR #222 does not duplicate those backend files.

### B-02 — High: frontend Factory destination conflicts with backend direct StateInit deployment

The Python adapter's CREATE_DEAL_ESCROW builder targets the deterministic per-deal escrow address and attaches its state_init_boc. The frontend transaction validator and TON Connect allowlist instead require factory_address and expect the deployment message to target a Factory. No Factory contract/source/ABI is pinned by DealEscrow v1. Agent #1 and technical lead must choose and sign off one topology; do not rewrite addresses, payloads or StateInit to make the two sides appear compatible.

### B-03 — High: API omits the mandatory ActivateDeal operation

The contract requires seller ActivateDeal before it accepts the NFT deposit. The standalone backend adapter builds deployment and activation as two distinct wallet messages/actions. The current API routes and seller available_actions expose create-deal-escrow and deposit-NFT but no activate route/action. When transaction preparation is eventually enabled, this leaves a missing lifecycle transition. Backend/API/frontend action types and persisted query IDs must be aligned with Agent #1 before enabling.

### B-04 — High: backend/API action surface is incomplete

The backend enum contains TIMEOUT_DEAL and RECOVER_UNEXPECTED_NFT, but no API prepare routes expose them. The API/frontend also expose withdraw_unsold_nft, while the pinned adapter has no implementation for WITHDRAW_UNSOLD_NFT; the contract's actual unsold-expiry path is TimeoutDeal. Reconciliation and product semantics must be agreed before mapping these labels to opcodes.

### B-05 — High: no configured finality provider or getter reconciliation

The provider is only an interface plus UnconfiguredTONTestnetEscrowProvider. It can describe finality-proof structures but does not fetch/verify masterchain inclusion, bind finalized traces, poll contract getters or verify current NFT ownership. ABI getters are not wired into a reconciliation worker. No indexer-only status may advance canonical deal state.

### B-06 — High: action payload persistence is incomplete

Durable action identity/idempotency records exist, but the exact unsigned TON Connect payload, payload digest, response metadata and retry replay are not yet produced by the API. A repeated idempotency key returns a durable action record/503, not the same prepared wallet payload. This is acceptable while blocked, but not ready for transaction preparation.

### B-07 — Medium: bounce handling is terminal-safe but not operation-aware

onBouncedMessage(_in: InMessageBounced) returns without mutation for terminal states and sends non-terminal deals to manual review. It ignores the bounce envelope and does not correlate sender, original destination/body, action, query ID or attempt with the pending outbound operation. Tests use synthetic bounced messages and do not cover every real contract-generated action-phase bounce. Manual review does not itself prove NFT return or principal settlement.

### B-08 — Medium: independent review and live acceptance have not occurred

No named independent TON/Tolk reviewer report or verified valueless testnet trace/getter/current-owner evidence is attached. Internal code review and successful emulator/serializer CI cannot substitute for those gates.

### B-09 — Medium: testnet router runtime-gate implementation was incomplete on the latest base

The latest main commit added test cases for an environment- and preview-mode-aware escrow router mount, but the implementation still mounted solely on TON_CONNECT_NETWORK and Settings did not define preview_mode. This branch adds the missing Settings field and helper: local/development/test/preview may mount only on testnet; production additionally requires explicit preview_mode=True; staging, an empty environment and mainnet remain blocked. The guard only controls HTTP router mounting and does not configure the transaction adapter, signer, broadcaster or chain provider.

### B-09 — Backend coordination and CI provenance

PR #222 overlaps backend files with PR #223. The canonical backend implementation is PR #223; keep the API fail-closed diagnostic builder, precise deployment_snapshot_incomplete classification and Preview mount policy there. Do not merge or cherry-pick both implementations independently. The latest observed #223 head is 89cb84a6950200a342c74427bddaddc387ef0a36. Green Backend/Frontend CI evidence currently available for #223 is for prior head c715b95fd116a22a1c30acc63478ca633eb64962 (Backend run #43717484891, Frontend run #43717484923); the current head's newest commit still requires exact-SHA CI verification. The ORM snapshot builder on #223 explicitly remains diagnostic-only; no complete immutable snapshot migration has landed.

## Deployment and acceptance checklist

Before transaction preparation is enabled:
1. Agent #1 + technical lead approve the immutable deployment snapshot, direct StateInit vs Factory topology, activation action, all query ID ownership/replay rules, unsigned payload persistence and API/frontend action names.
2. Add the missing immutable DB fields and constraints; update migrations and prove PostgreSQL concurrency and immutability with disposable test DB.
3. Implement a real testnet provider that independently verifies masterchain/shard inclusion and finality, exact transaction/message/trace identity, getter results and current NFT owner. Indexer flags are not finality proof.
4. Add and pass all missing timeout, failed outbound transfer, bounce/replay, action query-ID and terminal financial/NFT ownership tests. Use actual valid Ed25519 signatures on the end-to-end resolver/oracle paths.
5. Reconcile every getter (get_state, get_progress, get_deal_terms, get_oracle_keys, get_resolver_keys) against immutable snapshot and traces.
6. Obtain independent TON/Tolk contract audit and disposition all critical/high findings.
7. Only after explicit owner approval, run a valueless testnet lifecycle. Attach deployment StateInit/address, finalized transaction+message+trace proofs, getter snapshots, before/after balances/fees and NFT current-owner proof for each state transition.
8. Keep signing, wallet custody, broadcast automation and mainnet disabled until separate release approval.

## Explicit safety statement

No mainnet calls, real-value transfers, real NFT transfers, wallet signing, private keys or live testnet deployment were used in this review. This PR does not enable transaction preparation. The escrow remains a disabled, testnet-scoped prototype and is not testnet-accepted or production-ready.
